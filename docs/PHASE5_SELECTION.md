# Phase 5 — Viewport Selection Foundation

Phase 5 turns the Stage 4 renderer demo into an editor-aware viewport without moving authored or selection ownership into Vulkan.

## Ownership

```text
Android touch input
        |
        v
Native ViewportHost
  - Document
  - EditorHistory
  - EditorContext
  - persistent Object/Mesh identity
  - visible-object render list
        |
        v
MeshEvaluator -> RenderExtractor
        |
        v
VulkanViewport
  - GPU buffers
  - camera
  - derived CPU pick triangles
  - active-object overlay buffer
```

`Document` remains authored truth. `EditorContext` remains the owner of active-object and selection state. Vulkan keeps only derived render/pick data and never writes editable topology.

## Stage 5A exit gate

Stage 5A established the first persistent editor session and single-object selection path:

- the bootstrap cube lives in a persistent native `Document`, not a temporary renderer-local document;
- one-finger movement must cross Android touch slop before orbit begins;
- a one-finger tap ray-picks evaluated/extracted geometry;
- tapping geometry sets the engine-side active object and tapping empty space clears it;
- the selected object shows an outline plus XYZ origin/gizmo foundation;
- two-finger pan/pinch behavior from Stage 4 remains unchanged;
- ARMv7 and ARM64 CI/APK gates stay green.

## Stage 5B exit gate

Stage 5B generalizes that proof into a scene-ready object-selection boundary:

- `ViewportHost` owns a persistent list of visible `ObjectId` + extracted `ViewportMesh` snapshots;
- two persistent engine objects are present in the Android test scene;
- all visible geometry is batched for the current simple renderer without losing per-object identity;
- CPU picking chooses the nearest triangle across the complete visible batch;
- renderer-local synthetic vertex/face IDs are used only to disambiguate overlapping per-mesh IDs inside the batch;
- every pick is mapped back to the original stable `ObjectId` and original stable `sourceFace` before it reaches editor state;
- only the active object receives the orange outline and XYZ origin/gizmo overlay;
- selection-overlay buffer writes happen only after the previous frame fence signals;
- tapping empty space clears the active object and overlay;
- one-finger orbit and Stage 4 two-finger pan/pinch remain unchanged;
- ARMv7 and ARM64 CI/APK gates remain green.

The second test object is authored at an offset inside its own mesh only because `ObjectBlock` does not yet contain transform state. This is deliberately temporary. Phase 6 moves object placement into real engine-owned transforms and undoable transform commands instead of teaching Vulkan about authoring transforms.

## Picking contract

CPU ray/triangle picking runs over the same immutable evaluated render snapshots supplied to Vulkan. The ray is generated by inverting the live Vulkan view-projection matrix and unprojecting the touch point at Vulkan NDC depths 0 and 1.

Each visible object keeps its persistent engine `ObjectId`. Each extracted triangle keeps its original stable `sourceFace`. Because separate meshes may reuse the same local `VertexId` and `FaceId` numeric values, the renderer batch assigns renderer-local synthetic IDs while composing the batch. Those IDs never escape Vulkan-facing derived state: the native host receives the original stable object and face IDs.

The renderer does not return pointers, packed authoring indices, GPU allocation addresses, or synthetic IDs to editor state.

## Selection overlay

Selection feedback is a derived line overlay. Evaluated triangle edges are grouped by stable source vertex/face identity per object so triangulation diagonals from one authored face are omitted while real face boundaries remain. Each object has its own derived overlay plus an XYZ origin/gizmo foundation.

The GPU selection buffer is allocated once to the largest overlay needed by the current render list. A selection change records only the desired `ObjectId`; the actual host-visible buffer write is deferred until the render loop has waited for the previous frame fence. Command buffers are then re-recorded to draw only the active object's overlay.

## Input arbitration

A one-finger down begins as a tap candidate. Movement inside Android's `touchSlop` is ignored by the orbit camera. Once movement crosses the threshold the gesture locks to orbit and cannot become a tap. Any multi-touch participation permanently disqualifies that gesture from selection, preserving the Stage 4 two-finger pan/pinch recognizer.

## After Phase 5

The object-mode selection foundation is now ready for transform work. The next major phase is engine-owned object transforms and commands:

1. add position/rotation/scale to persistent object state;
2. make transforms undoable through `EditorHistory`;
3. derive render transforms and gizmo placement from engine state;
4. add gizmo-axis hit testing and Move interaction;
5. add Rotate and Scale after Move is stable.

Edit-mode face/edge/vertex selection can then build on the same stable `ObjectId` + source-element identity boundary without changing renderer ownership rules.
