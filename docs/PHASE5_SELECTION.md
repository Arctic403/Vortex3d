# Phase 5 — Viewport Selection Foundation

Phase 5 turns the Stage 4 renderer demo into an editor-aware viewport without moving authored or selection ownership into Vulkan.

## Ownership

```text
Android touch input
        |
        v
Native ViewportHost
  - Document
  - EditorHistory
  - EditorContext
  - persistent Object/Mesh identity
        |
        v
MeshEvaluator -> RenderExtractor
        |
        v
VulkanViewport
  - GPU buffers
  - camera
  - derived CPU pick triangles
  - selection/gizmo overlay buffers
```

`Document` remains authored truth. `EditorContext` remains the owner of active-object and selection state. Vulkan keeps only derived render/pick data and never writes editable topology.

## Stage 5A exit gate

- the bootstrap cube lives in a persistent native `Document`, not a temporary renderer-local document;
- one-finger movement must cross Android touch slop before orbit begins;
- a one-finger tap ray-picks the evaluated/extracted cube;
- tapping the cube sets the engine-side active object;
- tapping empty space clears the active object;
- the selected object shows an outline plus XYZ origin/gizmo foundation;
- two-finger pan/pinch behavior from Stage 4 remains unchanged;
- ARMv7 and ARM64 CI/APK gates stay green.

## Picking contract

Stage 5A uses CPU ray/triangle picking over the same immutable `ViewportMesh` snapshot supplied to Vulkan. The ray is generated by inverting the live Vulkan view-projection matrix and unprojecting the touch point at Vulkan NDC depths 0 and 1. Triangle hits return the `sourceFace` stable engine ID carried by `RenderExtractor`; the native host then resolves that hit to the persistent object and changes `EditorContext` state.

The renderer does not return pointers, packed authoring indices, or GPU allocation addresses.

## Selection overlay

The first visual selection feedback is a derived line overlay. Evaluated triangle edges are grouped by stable source vertex/face identity so triangulation diagonals from one authored face are omitted while real face boundaries remain. The same overlay buffer contains a small XYZ gizmo/origin foundation. Visibility is controlled by editor selection state and command buffers are re-recorded only after the previous frame fence signals.

## Input arbitration

A one-finger down begins as a tap candidate. Movement inside Android's `touchSlop` is ignored by the orbit camera. Once movement crosses the threshold the gesture locks to orbit and cannot become a tap. Any multi-touch participation permanently disqualifies that gesture from selection, preserving the Stage 4 two-finger pan/pinch recognizer.

## Deferred inside Phase 5

Stage 5A is object-mode selection for the current single-object viewport. The next increments are:

1. multi-object render draw items with object IDs attached to picking;
2. edit-mode face/edge/vertex selection using the same stable-ID boundary;
3. hover/active overlays;
4. interactive gizmo hit targets and transform commands once object transforms are authored engine state.

Those features build on this ownership boundary rather than bypassing it.
